# Subagent 委派验收：AI 专属判断层

## 分界线

```
scripts/quality-gate.mjs（机器做）       本 skill（AI 做）
────────────────────────────────── ──────────────────────────────────
build 通过                           交互流程是否符合角色工作流？
文件存在、路由配对、import 一致        按钮对当前角色+状态是否该出现？
权限/菜单/面包屑三件套齐全             空状态文案是否给用户有用信息？
组件内写死常量检测                     数据源是否与系统其他部分一致？
                                      菜单聚合是否符合业务域？
                                      视觉层级是否合理？（重要操作被埋没？）
                                      文案质量（不止禁用词，而是表达好坏）
```

**规则**：能写进 `scripts/quality-gate.mjs` 的，不要放在这里。

---

## AI 验收的四层判断

### 1. 工作流合理性（最难自动化）

不只看"有没有这个页面"，而是追问：

- 用户从哪个页面进入这里？完成后下一步去哪？这个页面在这个角色的工作流里**位置对吗**？
- 有没有漏掉应有的入口？比如 agent 做了页面但忘了在项目详情"当前阶段操作"里接线
- 有没有多余入口？比如把操作按钮放在了不相关的角色视角下

**判断方法**：切到该角色，从工作台出发走一遍完整路径，确认每个环节衔接自然。

### 2. 角色/状态条件审查（脚本 detect 不了逻辑错误）

脚本能发现"引用了不存在的变量"，但发现不了：

- `role === 'admin'` 写了但忘了 tenderer/agent 也能操作的情况
- 状态判断用了错误的状态字面量（比如 `status === '评审完成'` vs `status === 'evaluation-done'` 的旧值残留）
- 三个角色各应该看到什么按钮，实际少了一个

**判断方法**：脑中快速模拟三个角色 × 三个关键状态的矩阵，确认交叉格里的按钮正确。

### 3. 数据流连贯性（脚本只能查 import 存在，不能查语义正确）

- agent 在 SupplierLedger 里写死了 `PROJECT_NAMES` 映射，而 ProjectList 是从 `projectStore` 读的 → 两个地方的数据源不一致，项目改名后台账不同步
- agent 从 `project.packages?.[0]?.purchaseMode` 读采购方式，但 `purchaseMode` 可能挂在项目级别 → 读了空值
- store 种子数据和其他 store 的关联 ID 对不上（supplier 关联的 project ID 在 projectStore 里不存在）

**判断方法**：打开两个相关文件，对比同一个概念（项目名、采购方式、供应商名）的取值路径是否一致。不一致就是隐患。

### 4. UX 细节嗅觉（主观，但关键）

- 空状态文案是不是有用？"暂无数据"对用户没意义，"请等待采购截止后系统自动汇总"才有用
- 重要操作按钮是否在视线焦点？被 Table 滚动挡住？放在页面底部需要用户滚动才能发现？
- Tab 排序是否符合工作流顺序？监督大厅的 Tab 应该是 采购准备→响应→开启→评审→成交确认，而不是任意排序
- 表单字段是否过多？Modal 是否太宽？
- 搜索框 placeholder 是否明确（"供应商名称/统一社会信用代码"比"请输入关键字"好）

**判断方法**：打开页面，用 3 秒判断：最重要的动作是什么？我能一眼找到它吗？空数据时页面对我有用吗？

## 验收结论格式

每轮 agent 完成后，输出验收结论：

```
### Agent: xxx（做了什么）
- ✅ 工作流合理：页面入口/出口衔接正确
- ✅ 角色条件：已抽查 admin/bidder/tenderer 三个角色，按钮可见性正确
- ⚠️ 数据流：SupplierLedger 的 PROJECT_NAMES 写死，而 ProjectList 从 projectStore 读——不一致
- ⚠️ UX：空状态只写了"暂无数据"，建议改为"暂无响应数据，请等待采购截止后系统自动汇总"
- ❌ 角色遗漏：报价确认按钮 bidder 角色看不到，但需求要求 bidder 可确认

结论：打回修改数据流问题 + 角色遗漏；UX 建议为可选
```

每一行结论必须是**主观判断**（好东西/坏味道/错了），不是"文件存在"这种脚本能答的。

---

## 打回标准

| 问题类型 | 处理方式 |
|---------|---------|
| ❌ 工作流断裂、角色条件错误、数据流源不一致 | 打回重做（必须修） |
| ⚠️ UX 细节可改进（空状态文案、Tab 顺序、字段冗余） | 标注建议，可由父 agent 直接改 |
| ℹ️ 风格偏好（命名、缩进、文件组织） | 不改，除非违反项目约定 |

## 反例：这节课的验收失误

回顾 P1/P2 委派，我只做了脚本能做的（build 检查 + 文件存在确认），但跳过了 AI 该做的：

1. **数据流一致性**：SupplierLedger 的 PROJECT_NAMES 是写死的，和 projectStore 不同源——我没发现
2. **监督大厅 Tab 数据源**：`prepInfo` 从 `project.packages?.[0]?.purchaseMode` 取采购方式，但 purchaseMode 可能挂在项目上——我没验证数据路径
3. **UX 交互**：没有打开浏览器实测任何一个 agent 的页面——完全依赖 build 通过

**全是 AI 能发现但没去做的事。**

## Quick Reference

| 我该做什么 | 具体动作 |
